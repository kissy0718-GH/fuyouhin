# Phase 3：記事制作・AI下書き連携基盤

更新：2026-09-17

## 今回の範囲

企画 → 出典 → 構成 → 原稿登録 → ファクトチェック → 公開確認の制作フローを実装。AIサービスへの接続は未実施。課金・外部送信・自動記事生成は発生しない。

現状は生成先に渡す指示書を出力し、返された原稿を管理画面または専用REST APIで取り込む方式。検索意図・企画判断・構成は人が入力する。外部モデルによる自動提案・執筆・資料取得そのものは、サービス・認証方法・利用範囲を確定後に接続する。

## 管理画面

「情報確認 → 記事制作」を使用する。

1. キーワード、検索意図、CREATE / UPDATE / MERGE / NO ACTION、判断理由、独自の価値、構成、一次資料を保存する。UPDATEには元記事ID、MERGEには別の統合元記事IDも必要。
2. 制作する企画には資料を必須とする。資料不足の場合はNO ACTIONとして判断理由だけを残せる。資料はURL・名称・必要な要約に限定し、個人情報や取材原本は入れない。
3. 指示書を表示できる。資料内の命令を無視し、資料の範囲を超える情報を作らない指示を含む。更新の場合は現在の公開記事も含める。元記事が変わっていれば指示書の取得を止める。
4. 原稿・抜粋・主張リスト・生成元・モデル名を登録する。主張は必ず「要確認」で保存され、モデルの確認済み判定は採用しない。
5. 編集画面で必要な出典・確認日等を整える。確認担当が本文全体を読み、主張ごとに照合結果と根拠メモを記録する。原稿変更時は確認をやり直す。
6. 新規原稿は従来の公開確認画面で公開する。更新・統合案はそのまま単独公開できず、差分確認後に元記事へ採用する。

主張の種類は自治体・法律・料金・日付・URL・企業・営業時間・制度・その他。抜粋や見出しの有無を点検し、重複確認候補と内部リンク候補を表示する。キーワード一致は意味上の重複判定ではなく、人が検索意図を確認するための補助。

## 更新・統合の扱い

提案の保存は元記事を変更しない。企画作成時の内容ハッシュを保存し、採用時に元記事と照合する。元記事が変わっている場合は409で止め、新しい企画で検討する。

確認担当が明示的に採用した場合だけ、元記事の本文・タイトル・抜粋・基本出典・記事タイプを更新し、確認待ちへ戻す。公開中の元記事は一時的に非公開になる。元のslug・地域・品目分類は維持する。採用後のレコードでも事実確認と最終公開確認を行う。

採用前の本文・構造化情報・分類を非公開の企画メタ情報に保存し、WordPressの投稿リビジョンも作成する。完全な復元UIは未実装。MERGEでも統合元を自動削除・非公開化・転送しない。統合元の扱いは公開後の別の編集判断とする。

## APIと権限

専用ロール `cleanup_ai` は `read` と `cleanup_submit_drafts` のみ。アカウントや認証キーを自動作成しない。連携時は管理者が専用アカウントを作成し、HTTPS上のWordPress Application Password等の認証を利用する。秘密情報をリポジトリやブラウザー用JavaScriptに含めない。

- `GET /wp-json/cleanup/v1/ai/jobs/{id}`：準備済み企画の指示書。非公開の取材管理番号や編集メモは返さない。
- `POST /wp-json/cleanup/v1/drafts`：`job_id` と `output` を受け付け、articleのdraftを作る。公開状態、メタ情報、更新先は指定不可。

outputの必須項目は `title`, `content`, `excerpt`（空可）, `provider`, `model`, `claims`。claimsは `{ "claim": "確認対象の主張", "source_index": 0, "type": "other" }` の配列。出典番号は企画の出典を0から数える。生成元・モデル名は送信者の申告として保存する。

同じ企画・同じ原稿の再送は同じ下書きIDを返す。異なる原稿の再送は409。同時実行はWordPress optionsの一意キーで制御する。生成をやり直す場合は新しい企画を作る。適用処理は元記事単位でもロックする。

## 公開制御

AI専用ロールは企画変更、通常の投稿編集、公開、ファクトチェック承認、採用を行えない。事実確認結果は原稿と主張リストのハッシュに結び付け、本文の変更後は失効する。未確認・矛盾のある主張、実取材根拠のないスタッフ記事、調査条件のない料金記事は公開できない。

企画は非公開CPT `cleanup_ai_job` に保存し、公開カテゴリーを増やさない。標準RESTへ公開しない。追加出典のURL・名称は公開記事の資料一覧へ表示し、内部の照合メモ・申告モデル・指示書は公開しない。

## 検証と残る条件

2026-09-17、WordPress 7.1 / PHP 8.3 / Playground SQLiteで94項目の統合テストに合格。権限、資料不足、NO ACTION、必ず下書き保存、同一再送、異なる再送、主張の初期状態、元記事不変、採用時の競合、MERGEの非破壊性と、既存のSEO・公開制御を確認した。公開13ルート、不正2ルート、認証済み管理5画面、canonical・Schema・robots・転送・XMLサイトマップのHTTP確認にも合格。最新結果は `.runtime/test-result.txt`。制作企画の詳細画面全体のブラウザー操作確認は未実施。

- 外部モデル接続、AIによる企画・構成・執筆の自動実行、利用料金や品質の検証は未実施。
- 主張リストの漏れや資料の正確性をプログラムだけで証明できない。本文全体と一次資料を人が確認する。
- 処理途中の障害時は重複作成防止ロックを残す場合がある。企画のdraft_id、原稿、非公開バックアップを確認し、管理者が復旧する。自動再採用・強制ロック解除はしない。
- MySQL/MariaDBでの検証は引き続き必要。SQLiteでの成功を本番DBでの成功とは扱わない。
